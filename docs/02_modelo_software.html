1. Introducción

El presente documento constituye el Modelo de Software de Lavoro-ERP, describiendo en detalle la arquitectura técnica, el diseño de componentes, las clases del sistema, el modelo de base de datos relacional y los flujos de interacción entre los distintos elementos del sistema.

Este documento está orientado al equipo técnico (desarrolladores, arquitectos, DBAs) y es el complemento técnico al Diseño del Sistema de Información. Juntos conforman la documentación técnica completa del sistema entregado.

3. Arquitectura del Sistema

3.1 Patrón MVC (Modelo–Vista–Controlador)

Lavoro-ERP implementa una arquitectura MVC custom desarrollada sin framework externo (sin Laravel, Symfony ni CodeIgniter). Esto proporciona control total sobre el ciclo de vida de la aplicación y mínimas dependencias externas.

CapaResponsabilidadUbicación
Modelo (Model) Acceso y manipulación de datos. Consultas SQL, transacciones, reglas de negocio a nivel de datos. app/models/*.php
Vista (View) Renderizado HTML. Recibe datos del controlador y los presenta al usuario. Sin lógica de negocio. app/views/**/*.php
Controlador (Controller) Orquesta la lógica de la petición. Recibe la solicitud, invoca modelos, prepara datos y selecciona la vista. app/controllers/*.php
Router (App) Parsea la URL, determina el controlador y método a invocar, y ejecuta el flujo. core/App.php
Entry Point Único punto de entrada. Inicia sesión, configura el entorno, carga el Router. public/index.php

4. Descripción de Capas

4.1 Capa de Presentación (Vistas)

VIEW LAYER — app/views/

Las vistas son archivos PHP que reciben un array $data del controlador (vía extract($data)) y producen HTML dinámico. Todas las vistas se renderizan dentro del layout principal layouts/main.php.

Layout principal (main.php) incluye:

  • Declaración DOCTYPE, charset UTF-8, meta tags de no-cache
  • Carga de Bootstrap 5, Bootstrap Icons, Bootstrap Select, CSS personalizado
  • Variable global JavaScript window.BASE_URL y window.APP_URL
  • Barra de navegación superior (header) con logo y usuario autenticado
  • Menú lateral (sidebar) con navegación condicional según privilegios
  • Área de contenido principal donde se inyecta la vista específica

4.4 Capa de Infraestructura (Core y Config)

INFRASTRUCTURE LAYER — core/ + config/

Database.php — Patrón Singleton para conexión PDO

class Database { private static $instance = null; private $connection; public static function getInstance() { if (self::$instance === null) { self::$instance = new Database(); } return self::$instance; } public function getConnection() { return $this->connection; // PDO connection } }

La conexión PDO utiliza:

  • PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION — Errores como excepciones PHP.
  • PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC — Resultados como arrays asociativos.
  • charset=utf8mb4 — Soporte completo de Unicode incluyendo emojis.

El Singleton garantiza que solo exista una conexión a la BD durante todo el ciclo de vida de cada petición, evitando conexiones múltiples innecesarias.

6.3 Convenciones de la base de datos

ConvenciónDescripción
Eliminación lógicaLos registros no se eliminan físicamente. Se usa el campo estado con valores 'activo', 'anulado' o campo activo tinyint(1).
TrazabilidadTodos los registros operativos tienen creado_por (FK a usuarios), creado_en (DATETIME) e ip_creacion.
Correlativo de valesCalculado mediante MAX(NVale)+1 en cada módulo. Formato: prefijo + 6 dígitos con padding de ceros (ej: VDI-000042).
Charsetutf8mb4 con collation utf8mb4_general_ci para soporte completo de caracteres internacionales.
Zona horariaTodas las fechas se insertan en UTC-5 (America/Lima). El servidor PHP define la zona horaria antes de cualquier operación.
Claves primariasSiempre Id INT AUTO_INCREMENT PRIMARY KEY.
Sentencias preparadasToda interacción con la BD usa PDO prepared statements para prevenir SQL Injection (OWASP A03).

11.3 Implementación técnica

La bitácora se construye mediante consultas SQL UNION ALL sobre las tablas transaccionales de cada módulo, sin una tabla de log centralizada separada. Esto significa:

  • Los datos de auditoría se derivan directamente de los campos creado_por, creado_en, ip_creacion de cada tabla de cabecera, más las tablas de modificaciones asociadas.
  • La bitácora es siempre consistente con el estado real de la BD.
  • Soporta filtros combinados: módulo, acción, usuario, rango de fechas y número de vale.
  • Paginación de 50 registros por página.
