1. Introducción

1.1 Propósito del documento

El presente documento describe el Diseño del Sistema de Información del proyecto Lavoro-ERP, un sistema web desarrollado para la empresa Lavoro con el objetivo de digitalizar y centralizar los procesos de gestión logística interna y externa.

Este documento está dirigido al equipo de proyecto, al Project Manager, a los usuarios responsables de la operación del sistema y a cualquier auditor técnico que requiera comprender el alcance, las funcionalidades y el diseño general de la solución entregada.

1.2 Alcance

El sistema cubre los siguientes módulos funcionales:

  • Módulo de Recepciones Internas: Registro y gestión de vales de recepción interna (VRI) de materiales entre áreas de la empresa.
  • Módulo de Despachos Internos: Registro y gestión de vales de despacho interno (VDI) de productos hacia áreas internas.
  • Módulo de Recepciones Externas: Registro de recepciones de mercadería proveniente de proveedores o transportistas externos, incluyendo guías de remisión.
  • Módulo de Despachos Externos: Registro y control de salidas de mercadería hacia clientes o destinos externos con trazabilidad de transporte.
  • Módulos de soporte: Reportes, Auditoría/Bitácora, Administración de Usuarios y Roles, y Tablas Maestras.

Quedan fuera del alcance: módulos contables, facturación electrónica, control de inventario en tiempo real con stock mínimo/máximo y módulos de compras o proveedores.

2. Descripción del Negocio y Contexto

2.1 Contexto organizacional

Lavoro es una empresa dedicada a operaciones logísticas y de almacenamiento. Su operación diaria involucra el movimiento constante de mercadería entre áreas internas (almacenes, secciones de producción, distribución) y la recepción/despacho de materiales hacia y desde proveedores y clientes externos.

Antes de la implementación de Lavoro-ERP, el registro de estas operaciones se realizaba de forma manual (en papel) o mediante hojas de cálculo desconectadas, lo que generaba:

  • Pérdida de trazabilidad en los movimientos de mercadería.
  • Demoras en la consulta de información histórica.
  • Falta de control sobre quién realizó cada operación y cuándo.
  • Dificultad para generar reportes consolidados.
  • Riesgo de duplicación o pérdida de registros.

2.2 Problema o necesidad identificada

La necesidad central que motivó el desarrollo de Lavoro-ERP fue:

Digitalizar y centralizar los procesos de registro de recepciones y despachos (tanto internos como externos), garantizando trazabilidad completa, control de acceso por roles y disponibilidad inmediata de reportes consolidados en tiempo real.

3. Actores y Roles del Sistema

El sistema implementa un control de acceso basado en roles (RBAC). Cada usuario tiene un rol asignado, y cada rol puede tener múltiples privilegios. Los roles y sus responsabilidades principales son:

Rol Descripción Privilegios principales Acceso típico
Administrador Gestión total del sistema, configuración de usuarios, roles y tablas maestras. Acceso a auditoría completa. Todos los privilegios del sistema. Total
Operador Logístico Responsable del registro diario de recepciones y despachos internos. Puede imprimir vales. ver/crear/editar recepciones_internas, despachos_internos, reportes_internos. Módulos internos
Recepcionista Externo Responsable del registro de recepciones y despachos con proveedores y clientes externos. ver/crear/editar recepciones_externas, despachos_externos, reportes_externos. Módulos externos
Supervisor / Reportes Usuario con acceso de solo lectura y consulta de reportes consolidados. No puede crear ni modificar registros operativos. ver_reportes, ver_auditoria, exportar_excel. Solo consulta

4. Requerimientos Funcionales

Los requerimientos funcionales están organizados por módulo y numerados de forma correlativa.

4.1 Módulo de Autenticación y Seguridad

RF-01 — Inicio de sesión con credenciales
Descripción: El sistema debe permitir a los usuarios autenticarse mediante nombre de usuario y contraseña.
Actores: Todos los usuarios.
Flujo principal: El usuario ingresa credenciales → El sistema valida contra la BD → Si son correctas, inicia sesión y redirige al inicio.
Flujo alternativo: Si las credenciales son incorrectas, se muestra mensaje de error sin revelar cuál campo es incorrecto.
Notas: La contraseña se almacena con hash seguro (bcrypt mediante password_hash()).
RF-02 — Cierre de sesión
Descripción: El usuario puede cerrar su sesión de forma explícita desde el menú de perfil.
Actores: Todos los usuarios.
Notas: Se destruyen todas las variables de sesión del servidor.
RF-03 — Cierre de sesión automático por inactividad
Descripción: El sistema cierra automáticamente la sesión tras un período de inactividad, mostrando un mensaje de aviso al usuario.
Actores: Todos los usuarios.
RF-04 — Control de acceso basado en privilegios
Descripción: Cada funcionalidad del sistema verifica que el usuario tenga el privilegio correspondiente antes de mostrar el módulo o ejecutar la acción.
Actores: Sistema (automático).
Notas: Si el usuario no tiene el privilegio, se muestra mensaje de acceso denegado.
RF-05 — Protección de rutas no autenticadas
Descripción: Cualquier intento de acceso a una URL del sistema sin sesión activa redirige al inicio de sesión.
Actores: Sistema (automático).

4.2 Módulo de Recepciones Internas

RF-06 — Registro de recepción interna
Descripción: El sistema permite registrar un nuevo Vale de Recepción Interna (VRI) con sus datos de cabecera y lista de productos.
Datos de cabecera: Correlativo automático (VRI-XXXXXX), fecha, hora, turno, área, subárea, despachador, verificador, medio de transporte, N° de liquidación.
Datos de detalle: Código de producto, descripción, unidad de medida, cantidad, comentarios (uno o más productos por vale).
Actores: Operador Logístico, Administrador.
Reglas: El correlativo se genera automáticamente y es único. El sistema registra quién creó el vale y desde qué IP.
RF-07 — Consulta y listado de recepciones internas
Descripción: El sistema muestra un listado paginado de todos los VRI registrados con opción de búsqueda y filtrado por fecha, estado y correlativo.
RF-08 — Modificación de recepción interna
Descripción: Los vales VRI pueden ser modificados siempre que estén en estado activo. El sistema registra cada modificación en la bitácora.
RF-09 — Anulación de recepción interna
Descripción: Un VRI puede ser anulado indicando un motivo. El vale queda marcado como anulado pero no se elimina de la BD (no se borra, solo cambia estado).
RF-10 — Impresión de vale de recepción interna
Descripción: El sistema genera una vista imprimible del VRI en formato A4, incluyendo todos los datos del encabezado, la lista de productos y espacios para firmas.

4.3 Módulo de Despachos Internos

RF-11 — Registro de despacho interno
Descripción: El sistema permite registrar un nuevo Vale de Despacho Interno (VDI).
Datos de cabecera: Correlativo automático (VDI-XXXXXX), fecha, hora, turno, área, subárea, despachador, recepcionista, verificador.
Datos de detalle: Código de producto, descripción, unidad de medida, cantidad, comentarios.
RF-12 — Consulta y listado de despachos internos
Descripción: Listado paginado con filtros de búsqueda por fecha, estado, correlativo y área.
RF-13 — Modificación con límite de versiones
Descripción: Los VDI pueden ser modificados hasta un número máximo de veces configurable. El sistema valida el límite antes de permitir la modificación e informa cuántas modificaciones han sido realizadas.
Reglas: Al alcanzar el límite, el sistema bloquea modificaciones adicionales.
RF-14 — Anulación y reactivación de despacho interno
Descripción: Un VDI puede ser anulado con motivo y posteriormente reactivado si el usuario tiene el privilegio correspondiente.
RF-15 — Impresión de vale de despacho interno
Descripción: Vista imprimible del VDI con datos completos y firmas del despachador, recepcionista y verificador.

4.4 Módulo de Recepciones Externas

RF-16 — Registro de recepción externa
Descripción: El sistema permite registrar un VRE con datos del vehículo y transportista.
Datos de cabecera: Correlativo (VRE-XXXXXX), fecha, hora, turno, origen, recepcionista, empresa transportista, RUC, chofer, brevete, comentarios.
Datos de guías: Una recepción puede tener múltiples guías de remisión, cada una con su serie, número y lista de productos asociados.
RF-17 — Consulta API externa de DNI / Carnet (Factiliza)
Descripción: Al ingresar el DNI del chofer, el sistema consulta automáticamente una API externa (Factiliza) para autocompletar nombre y brevete.
Notas: Los resultados se cachean localmente para reducir llamadas a la API.
RF-18 — Gestión de guías de remisión
Descripción: Cada VRE puede contener N guías de remisión. Cada guía tiene serie, número y N productos asociados con cantidad y unidad de medida.
RF-19 — Modificación de recepción externa
Descripción: Los datos del VRE pueden ser modificados desde la vista de reporte, incluyendo actualización de productos específicos sin modificar los demás.
RF-20 — Anulación de recepción externa
Descripción: Un VRE puede ser anulado con registro del motivo y del usuario que realizó la anulación.

4.5 Módulo de Despachos Externos

RF-21 — Registro de despacho externo
Descripción: Registro de salida de mercadería a destinos externos.
Datos: Correlativo (VDE-XXXXXX), fecha, turno, destino, cliente externo, transportista, chofer, placa, hora de salida, productos con cantidades.
RF-22 — Validación de límite de modificaciones
Descripción: Similar al módulo interno, los VDE tienen un límite de modificaciones permitidas con validación explícita.
RF-23 — Anulación y reactivación de despacho externo
Descripción: Un VDE puede ser anulado indicando motivo y reactivado por usuarios con privilegio específico.

4.6 Módulo de Reportes

RF-24 — Reportes por módulo con filtros
Descripción: El sistema genera reportes de cada módulo (Despachos Internos, Recepciones Internas, Recepciones Externas, Despachos Externos) con filtros por rango de fechas, estado (activo/anulado) y otros criterios específicos.
Vistas disponibles: Despachos Internos, Recepciones Internas, Recepciones Externas, Despachos Externos, Reporte Consolidado, Reporte Picking, Liquidadas.
RF-25 — Exportación a Excel
Descripción: Cualquier reporte puede ser exportado a formato Excel (.xlsx) con encabezados formateados, usando la librería PhpSpreadsheet.
RF-26 — Edición en línea desde reportes
Descripción: Desde la vista de reportes, los usuarios autorizados pueden editar productos específicos de un vale sin necesidad de abrir el formulario completo de edición.

4.7 Módulo de Auditoría

RF-27 — Bitácora consolidada de operaciones
Descripción: El sistema mantiene un log centralizado de todas las operaciones de creación y modificación de los 4 módulos principales, con información de usuario, fecha/hora, IP y datos del registro afectado.
Filtros disponibles: Módulo, acción (creación/modificación), usuario, rango de fechas, N° de vale.
RF-28 — Historial de versiones por registro
Descripción: Al consultar la bitácora, el usuario puede ver el historial completo de modificaciones de un registro específico (comparativa de versiones).

4.8 Módulo de Administración de Usuarios y Roles

RF-29 — CRUD de usuarios
Descripción: El administrador puede crear, consultar, editar y desactivar usuarios. Incluye asignación de rol, documento de identidad y nombre completo.
RF-30 — CRUD de roles y asignación de privilegios
Descripción: El administrador puede crear roles y asignar a cada rol los privilegios específicos del sistema (granularidad a nivel de acción).
RF-31 — Exportación de usuarios a Excel
Descripción: El listado de usuarios puede exportarse a Excel con todos sus datos (excepto contraseñas).

5. Requerimientos No Funcionales

#CategoríaRequerimientoCriterio de aceptación
RNF-01Rendimiento Las páginas de listado y formularios deben cargarse en menos de 3 segundos bajo condiciones normales de red. Medición con herramientas de desarrollo del navegador en red LAN.
RNF-02Disponibilidad El sistema debe estar disponible 24/7 con una disponibilidad mínima del 99% mensual. Monitoreo de uptime del servidor de hosting.
RNF-03Seguridad Todas las contraseñas deben almacenarse con hash bcrypt. Las consultas a BD deben usar sentencias preparadas (PDO) para prevenir inyección SQL. Revisión de código fuente. Sin contraseñas en texto plano en BD.
RNF-04Seguridad Todas las salidas de datos hacia HTML deben estar escapadas (htmlspecialchars) para prevenir XSS. Revisión de vistas. Sin scripts ejecutables inyectados.
RNF-05Usabilidad La interfaz debe ser responsiva y funcional en resoluciones de escritorio (1024px+) y tablets (768px+). Pruebas en Chrome y Edge en distintas resoluciones.
RNF-06Mantenibilidad El código debe seguir la arquitectura MVC definida, con separación clara de responsabilidades entre controladores, modelos y vistas. Revisión de estructura de carpetas y archivos.
RNF-07Portabilidad El sistema debe ser desplegable tanto en entorno local (WAMP/XAMPP) como en hosting compartido o VPS con PHP 7.4+ y MySQL 5.7+. Despliegue verificado en ambos entornos.
RNF-08Trazabilidad Toda operación de creación y modificación debe quedar registrada en la bitácora de auditoría con usuario, fecha/hora e IP. Verificación en módulo de auditoría tras cada operación.
RNF-09Integridad Los registros nunca se eliminan físicamente (eliminación lógica mediante campo estado). Se preserva el historial completo. Verificación en BD: registros anulados permanecen con estado='anulado'.
RNF-10Compatibilidad El sistema debe funcionar correctamente en Google Chrome 90+, Mozilla Firefox 88+ y Microsoft Edge 90+. Pruebas funcionales en los navegadores indicados.
RNF-11Escalabilidad La arquitectura debe soportar la incorporación de nuevos módulos sin modificar la estructura base del framework MVC. El router y el framework base son genéricos y no dependen de módulos específicos.
RNF-12Backup El sistema debe incluir funcionalidad de respaldo de la base de datos ejecutable desde la interfaz de administración. Generación exitosa de archivo SQL de respaldo.

7. Especificación de Casos de Uso

CU-01 — Registrar Vale de Recepción Interna (VRI)

IdentificadorCU-01
NombreRegistrar Vale de Recepción Interna
Actor principalOperador Logístico
Actores secundariosSistema (genera correlativo, registra auditoría)
PrecondicionesEl usuario debe estar autenticado y tener el privilegio crear_recepciones_internas.
Flujo principal 1. El usuario navega al módulo de Recepciones Internas.
2. El sistema muestra el formulario de nueva recepción y genera automáticamente el correlativo siguiente (VRI-XXXXXX).
3. El usuario selecciona: turno, área, subárea, despachador, verificador, medio de transporte.
4. Opcionalmente ingresa N° de liquidación.
5. El usuario agrega uno o más productos con: código, descripción, unidad de medida, cantidad y comentarios.
6. El usuario hace clic en "Guardar".
7. El sistema valida los datos, inserta el registro en la BD y registra la acción en la bitácora de auditoría.
8. El sistema muestra confirmación de éxito con el correlativo asignado.
Flujos alternativos 3a. Si el usuario no ha seleccionado un área/subárea, el sistema muestra error de validación.
5a. Si no se agrega ningún producto, el sistema advierte que debe incluir al menos uno.
7a. Si la BD no está disponible, el sistema muestra error técnico genérico.
PostcondicionesEl VRI queda registrado en estado "activo" con correlativo único, fecha/hora y datos del creador.

9.2 Flujo de registro de Recepción Externa (VRE)

1
Apertura del formulario: El usuario accede al módulo de Recepciones Externas. El sistema carga automáticamente el siguiente correlativo disponible (VRE-XXXXXX), la fecha actual y la hora del sistema.
2
Ingreso de datos del transportista: El usuario selecciona el origen, turno y recepcionista, e ingresa el RUC/empresa del transportista. Puede seleccionarlo del combo o buscarlo.
3
Consulta de DNI del chofer (API): El usuario ingresa el DNI del chofer. El sistema consulta la API Factiliza en tiempo real y autocompleta nombre completo y número de brevete. Si la API falla, el usuario lo ingresa manualmente.
4
Registro de guías de remisión: El usuario agrega las guías de remisión asociadas a la recepción (serie + número). Puede agregar múltiples guías por vale.
5
Detalle de productos por guía: Para cada guía, el usuario ingresa los productos recibidos: código (búsqueda en catálogo), descripción, unidad de medida y cantidad.
6
Guardado: El sistema valida todos los datos, realiza la inserción en tres tablas (VRE, guías, productos) dentro de una transacción. Si alguna falla, se revierte todo.
7
Confirmación y registro en auditoría: El sistema retorna un JSON con éxito, muestra la confirmación al usuario y registra automáticamente la acción en la bitácora (módulo, usuario, IP, timestamp).
